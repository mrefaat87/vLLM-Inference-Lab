Phase 3 — Should a Worker Decide Its Own Limits?

68 experiments across 4 admission strategies, 2 models, and 4 bottleneck metrics • Qwen2.5 AWQ on NVIDIA T4 (g4dn.xlarge Spot, $0.22/hr) • EKS + Karpenter + vLLM v0.4.1 • April 5–8, 2026

The Question
Can a worker regulate its own load better than a fixed queue limit?
The Answer
It depends on the bottleneck
7B: no (vLLM handles it). 14B: yes (KV-scarce).
The Surprise
Cost model accuracy > metric choice
Adaptive EMA recovers 10% throughput by fixing cost overestimates

1 The Setup

In a queue-based inference architecture, RabbitMQ pushes jobs to the worker (via AMQP basic_consume), which runs them through vLLM and streams tokens back. The worker controls backpressure via prefetch_count — how many unacknowledged messages the broker will deliver at once. The core question: how many concurrent requests should a single GPU worker accept?

We tested four increasingly sophisticated answers:

static "Just set a fixed limit"

RabbitMQ prefetch_count=N caps concurrency. No runtime intelligence. Like a fixed-size Auto Scaling Group — simple, predictable, but blind to actual load.

reactive "Check if the system is hot"

Before admitting a request, check current GPU/memory utilization. If above threshold, reject. Like target-tracking on CPU — responsive but doesn't consider what the incoming request will cost.

predictive "Estimate what this request will cost"

Before admitting, estimate the request's resource footprint using max_tokens. Project post-admission load. Like predictive scaling — smarter, but the estimate might be wrong.

adaptive "Learn what requests actually cost"

Like predictive, but learns the actual output_ratio (fraction of max_tokens used) via EMA from completed requests. Inspired by SGLang's new_token_ratio. Self-correcting.

We swept each strategy's aggressiveness parameter across 4 bottleneck metrics (decode throughput, GPU compute, KV cache, compound) on two models: 7B (where memory bandwidth is the bottleneck) and 14B (where KV cache headroom is tight). The SLA target is 2× the uncontested baseline TPOT.

2 Act I: Can We Beat "Just Set prefetch=N"? (7B, Rounds A–C)

Our first hypothesis: a worker that monitors its own resource usage should outperform a fixed concurrency limit. We tested this on the 7B model across three bottleneck metrics, expecting reactive and predictive to show clear advantages.

The result was humbling. Static won every round. Here's how we got there.

What if we made KV cache the actual bottleneck?

3 Act II: Making It Hard Enough to Matter (14B, Round D)

We switched to the 14B model (Qwen2.5-14B-Instruct-AWQ). On T4 with 0.90 GPU memory utilization, this model leaves only ~5.3 GB for KV cache. Each XL request (660 input + 2048 output tokens) uses ~587 MB of KV. At 8 concurrent XL requests: 4.7 GB = 89% of the KV budget. Now the system is genuinely constrained.

Workload: kv_stress_14b — 0.15 req/s, all XL prompts, 300s duration. Each request takes ~128s to complete.

Predictive's per-request KV cost estimation finally matters — it gates expensive requests before they trigger preemption cascades.

Three conditions made the difference: (1) KV cache held for full request lifetime (not released per-token like decode), (2) hardware has tight headroom (5.3 GB for a 587 MB-per-request workload), (3) 147× request size variance (20 vs 2048 tokens). When all three hold, per-request cost estimation earns its keep.

But predictive has a flaw exposed in Rounds A–C: its cost model uses max_tokens as worst-case output. On 7B, requests use only ~35% of their budget, causing 3× overestimation. On 14B with all-XL requests, this doesn't matter (requests use nearly 100%). But what about mixed workloads? What if the cost model could learn?

4 Act III: Teaching the Worker to Learn (Adaptive, Rounds E–F)

Industry research (SGLang's new_token_ratio, QLM's wait-time estimator) showed that production systems use self-correcting cost models rather than static worst-case estimates. We implemented the same idea: an EMA-tracked output_ratio that learns what fraction of max_tokens requests actually use.

// The adaptive feedback loop

ADMIT: cost = max_tokens × output_ratio // starts at 1.0 (= predictive)
SERVE: vLLM generates tokens, request completes
LEARN: ratio = α × (actual_output / max_tokens) + (1-α) × ratio // EMA update
PRESSURE: vLLM error → ratio snaps to max(current, 0.80) // safety valve

// On 7B: ratio converges to ~0.35 (requests use 35% of budget) → 3× less conservative
// On 14B: ratio stays ~1.0 (XL uses full budget) → same as predictive

We tested three learning rates (α=0.05, 0.10, 0.20) on both models. If adaptive works, it should approach static's throughput on 7B (by correcting the overestimate) while maintaining predictive's quality on 14B (by not under-correcting).

Key Insights

When external admission control adds value: Three conditions must hold simultaneously: (1) bottleneck resource held for full request lifetime (KV cache), (2) hardware has tight headroom (14B on T4), (3) request sizes vary significantly (20 vs 2048 tokens). When any condition is missing, vLLM's internal scheduler is sufficient.
Adaptive's niche: Adaptive improves over predictive when the cost model overestimates (requests use <100% of max_tokens). On 7B, it recovers 10% throughput. On 14B where the cost model is accurate, it converges toward predictive and adds no value. The strategy's value is workload-dependent, not model-dependent.

Infrastructure Lessons

kubectl Context Drift

Multiple EKS clusters caused silent context switches mid-sweep. Fix: isolated KUBECONFIG per cluster.

Rollout Restart Required

kubectl set env + maxSurge=0 = stale pods. Fix: rollout restart after every env change.

Probe Timeout

3 retries (30s) too short for model reload (~3 min). Fix: 18 retries (180s).

EKS Access Entry

Karpenter node role missing from access entries. GPU nodes launched but couldn't register.

The Narrative Arc

We started asking "which metric should we gate on?" and ended up learning that the metric choice doesn't matter — the cost model accuracy does.

Rounds A–C tried three different bottleneck metrics on 7B. All produced the same answer: static wins. The external gate couldn't beat vLLM's internal scheduler because the bottleneck (bandwidth) is shared equally.

Round D changed the game by switching to 14B, making KV cache the real constraint. Suddenly predictive's per-request cost estimation mattered — it could distinguish a 4 MB request from a 587 MB one.

But predictive's flaw was exposed: it uses max_tokens as worst case, overestimating by 3× on 7B. Adaptive (SGLang's new_token_ratio pattern) fixed this with an EMA that learns actual usage, recovering 10% throughput on 7B while producing the best TPOT of any strategy (34ms).

On 14B, adaptive correctly converges toward predictive — when the cost model is already accurate, there's nothing to learn. The engineering lesson: adaptive vs static cost estimation is the lever, not which resource to gate on.
