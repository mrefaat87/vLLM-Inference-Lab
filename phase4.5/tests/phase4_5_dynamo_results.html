Phase 4.5 — NVIDIA Dynamo Hands-On Spike

Going through the motions of deploying NVIDIA Dynamo end-to-end on AWS commodity GPUs. Three experiments — co-located baseline, KV-aware routing, prefill/decode disaggregation — on 4× g4dn.xlarge T4 spot instances with Dynamo v1.0.2.

Why this spike

Original project plan slated NVIDIA Dynamo for Phase 8 (full disaggregated inference platform). Interview timing forced an earlier hands-on encounter — a 1-day, time-boxed spike to deploy Dynamo on an EKS GPU fleet, exercise its three differentiating features (Smart Router, disaggregation, NIXL KV transfer), and document everything that broke or was non-obvious along the way.

A first attempt on 2026-05-01 hit the AWS spot G/VT vCPU quota wall on g5.8xlarge spot (EFA-equipped). Pivoted to g4dn.xlarge T4 — the same instance Phase 2-3 used and known-good — accepting that we'd lose the EFA / NIXL-on-RDMA story and gain a spike that actually runs to completion. That trade turned out to produce a more interesting finding: NIXL on commodity AWS networking is a deopt, and we measured the cost.

Setup

Compute

4 × T4 GPUs

g4dn.xlarge spot, 16 GiB VRAM, 4 vCPU, 1 GPU per node. Single AZ us-east-1a. $0.235/hr per node.

Stack

v1.0.2

Dynamo Platform chart pinned to v1.0.2 git tag. vLLM runtime image nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.0.2. etcd, NATS, PostgreSQL, MinIO as control-plane deps.

Workloads

4 profiles

W1 random short, W2 shared-prefix RAG, W3 bursty long-prompt mix, W4 cold-start probe. ~1000 inference requests across all runs.

Observability: kube-prometheus-stack with DCGM ServiceMonitor wired up. Phase 3-compatible JSON output schema for results, refuses to overwrite on re-run.

Experiments

A — Baseline colocated

4 vLLM workers, prefill+decode on the same GPU. Round-robin routing. The reference everything else compares to.

B — KV-aware routing colocated

Same topology as A. Frontend changed to --router-mode kv --router-kv-events. Variable: router only.

C — Disaggregation TCP NIXL

2 prefill + 2 decode workers, NIXL transport over TCP (no EFA). Variable: topology only.

D (ModelExpress vs Phase 4.1 streamer) was skipped per the plan's drop-priority list once A/B/C produced a clean disagg-without-EFA finding — would have needed a separate ModelExpress server install for less interview value than what we already had. E (speculative decoding) was dropped during planning — 7B-AWQ + 0.5B draft + KV cache too tight on T4 16 GB.

What's happening: Disaggregation splits prefill and decode onto separate g4dn nodes. Every request hits the prefill worker, KV blocks get computed, then transfer over NIXL to the decode worker. Without RDMA hardware, NIXL falls back to TCP — and on g4dn.xlarge's commodity 25 Gbps networking, that transfer costs ~700–1100 ms per request. That's bigger than any head-of-line-blocking savings disagg is supposed to deliver.

Why this matters for the interview

The interview talking point isn't "disagg is bad." It's: disagg's value is gated on RDMA-class networking, and most AWS GPU instances don't have it. On bare-metal H100 clusters with InfiniBand, the same architecture would likely flip to a 2× win. We measured the cost of the missing fabric, which is exactly the AWS-specific story the spike was designed to tell.

TBT p50 is essentially flat across all three experiments (224-240 ms) — the per-token decode cost is the same regardless of topology. The hit is entirely concentrated at TTFT, which is exactly where you'd expect the cross-node KV transfer to land.

KV-aware routing — modest p99 win on bursty traffic, near-noop elsewhere

Identical TTFT to round-robin on W1 and W2, with one outlier: W3 (bursty long-prompt mix) p99 dropped from 1009 ms → 899 ms — a 11% improvement. Three plausible reasons it didn't show more:

  • 4 workers is too few. Round-robin already lands the same request on the same worker fairly often (probability 1/4), so the KV router has limited headroom to optimize cache placement.
  • W2's 2 KB shared prefix is small relative to total prefill. Dynamo's router can route to a cache-warm worker, but the user-message-specific prefill still dominates ~700 ms TTFT. The cache hit saves a small fraction.
  • vLLM's per-worker prefix caching covers most of the win once a worker has seen the prefix. The KV router shines when you're trying to steer traffic to where caches exist; if engine-side caching already captures the prefix on every hit, the routing layer's marginal value is small.

Implication: KV-aware routing's payoff scales with fleet size and prefix-share ratio. A 32-worker fleet running real RAG (longer shared prompts, more worker diversity for round-robin to miss) would likely show a 2-3× larger delta than what we measured at 4 workers with a 2 KB prefix.

Operator quirks that ate the most time

Worker-suffix namespace mismatch

The Dynamo operator injects DYN_NAMESPACE=dynamo-system-exp-X on Frontend pods, but workers append a hash suffix (DYN_NAMESPACE_WORKER_SUFFIX=<8 hex chars>) and register their model cards under the full dynamo-system-exp-X-<suffix> Dynamo namespace. Frontend's /v1/models returned empty until we manually overrode DYN_NAMESPACE on Frontend to include the worker suffix: 

kubectl patch dynamographdeployment exp-a-baseline --type=merge \
  -p '{"spec":{"services":{"Frontend":{"envs":[{"name":"DYN_NAMESPACE",
       "value":"dynamo-system-exp-a-baseline-<suffix>"}]}}}}'

Workaround is fragile — every redeploy generates a new hash, requiring a re-patch. Feels like an operator bug or undocumented contract; would file an upstream issue if I were on the team.

Disagg requires explicit NIXL connector flag

The --connector flag is deprecated in v1.0.2. The new contract is: 

--kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_both"}'

Old example DGDs in the v1.0.2 source don't have this. Prefill workers crash on first boot with a clear error message, but the operator silently keeps both old (broken) and new (patched) ReplicaSets, leading to the next quirk:

Stale ReplicaSet pile-up on rolling update

When patching the DGD spec, the operator created a NEW worker deployment hash but didn't terminate the OLD one. Result: 6 worker pods wanted on 4 GPU nodes (anti-affinity by hostname), 2 pending forever, deadlock. Fix: 

kubectl delete deploy <old-hash>
# OR worst-case, nuke the DGD and re-apply

Infrastructure surprises

  • AWS Spot G/VT vCPU quota is per-account-per-region, defaults to 32 vCPU. 4× g5.8xlarge = 128 vCPU = blocked. Karpenter's MaxSpotInstanceCountExceeded masquerades as a transient capacity event. Pre-flight check before sizing any multi-GPU spot fleet.
  • Bitnami Mid-2025 image-hosting change broke many Helm charts. Dynamo platform chart depends on bitnami/etcd:3.6.4 which 404s on fresh pulls. Replaced etcd / postgres / minio with plain manifests pointing at official images (quay.io/coreos/etcd, postgres:16-alpine, minio/minio).
  • Dynamo main chart references image tag that doesn't exist on NGC. Listed tags via NGC's unauth token endpoint; latest stable image is 1.0.2. Pinning to the v1.0.2 git tag of the chart aligned versions.
  • EKS 1.30 doesn't ship a gp3 StorageClass by default — only gp2. Created and patched as default; otherwise the Bitnami values' storageClass: gp3 fail with PVCs Pending forever.
  • Tooling Cluster-guard hook didn't recognize helm's --kube-context flag (only kubectl's --context). Patched the regex to recognize both — reusable hook fix that survives the spike.
  • Misc Networking blips during Terraform apply (DNS lookup failures mid-create for eks.us-east-1.amazonaws.com and iam.amazonaws.com) left the EKS cluster ACTIVE but TF state inconsistent. Re-running terraform apply reconciled — except an orphan EKS cluster needed manual aws eks delete-cluster first.

What I'd say in the interview

  1. "I built and exercised Dynamo end-to-end on EKS with T4 GPUs in a few hours." Schema-correct DGDs for co-located, KV-aware-routing, and disaggregated topologies; full Prometheus + Grafana with DCGM scraping.
  2. "I measured the cost of disaggregation without RDMA on AWS commodity instances: roughly 2× TTFT regression on T4 + TCP-NIXL." Concrete numbers, three workload patterns, four T4 nodes. Empirically grounded — not handwave.
  3. "KV-aware routing's win scales with fleet size and prefix-share ratio." Modest 11% p99 improvement at 4 workers. Natural follow-up is to repeat at 16-32 workers with longer shared prefixes.
  4. "The operator's discovery-namespace contract has a sharp edge." Frontend's DYN_NAMESPACE doesn't include the worker hash suffix that workers append. First-deploy /v1/models is empty until you patch.
  5. "NIXL is portable to commodity AWS GPUs without specialized networking — it just falls back to TCP, which is slow but functional." Means you can prototype disagg architectures without paying for p4d/p5 hardware first.
  6. "vLLM's per-worker prefix caching covers most of the KV-routing win when prefixes are small." The router earns its keep on workloads where prefix is large or the fleet is too big for round-robin to randomly hit warm workers.
  7. "Time-to-first-deployment-that-served-tokens was about 5 hours." Most was schema mismatches and namespace gotchas, not infrastructure provisioning. Production teams adopting Dynamo should expect 2-3 days of operability investment before benchmarks are meaningful.

Open questions / follow-ups

  • NIXL EFA performance on AWS — out of scope after the T4 pivot. Would need g5.8xlarge or g6.8xlarge (EFA-equipped) to measure properly. Candidate for a future Phase 4.6: even half a day on EFA hardware would close the disagg-economics question.
  • KV router behavior at higher concurrency / fleet size — measured at 4 workers and 1.5–2 req/s. Production-scale (32 workers, 50+ req/s) would likely show a larger router delta.
  • ModelExpress vs Phase 4.1 streamer head-to-head — skipped (Experiment D).
  • Speculative decoding on T4 — dropped during planning; 7B-AWQ + 0.5B + KV cache too tight on 16 GB. Future spike on 24 GB+ GPUs unlocks E.
