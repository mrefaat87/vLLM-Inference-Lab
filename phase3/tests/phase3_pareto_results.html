1 Executive Summary

On 7B (Rounds A–C), static prefetch=3 wins every round. Across three different bottleneck metrics (decode_throughput, gpu_compute, compound), the same result appears: vLLM's internal scheduler handles bandwidth-bound decode perfectly. External admission control only adds latency and NACKs. 100% SLA compliance, 87–88 tok/s throughput, zero rejections.
On 14B (Round D), predictive with threshold=0.50 is the only config that keeps TPOT under SLA. When the model is large enough to exhaust KV cache on T4, the bottleneck shifts from memory bandwidth to VRAM capacity. Predictive's per-request KV cost estimation finally differentiates — it can gate requests before they cause preemption storms. TPOT P95 = 94.76ms vs SLA target of 124.64ms.
Why Static Wins on 7B

On a memory-bandwidth-bound GPU like T4, vLLM's internal continuous batching scheduler already optimizes decode throughput. An external admission controller cannot see or influence the internal batch composition — it can only delay or reject requests, adding latency without improving per-token decode speed.

Why Predictive Wins on 14B

With a 14B model, each request's KV cache footprint is large enough to exhaust T4's 16 GB VRAM. The predictive gate estimates per-request KV cost before admission, preventing the pathological case: too many concurrent long-context requests causing preemption storms that waste already-computed tokens. This is the capacity-bound regime where external admission control earns its keep.

Why Reactive Always Fails

Reactive strategies generated 73,000–121,000 NACKs across rounds. The retry churn inflated TTFT and dropped SLA compliance. The gate fires on current utilization, but utilization fluctuates naturally — rejecting requests doesn't reduce the fluctuation, it just adds a thundering-herd retry storm on top.

2 Background & Motivation

Three Prior Flawed Rounds

  • Round 1: Used remote /metrics HTTP polling to read vLLM state. Added 50–200ms per admission decision. The polling itself became the bottleneck.
  • Round 2: Gated on KV cache utilization, but KV cache never exceeded 25% under the test workload. The gate never fired — all strategies looked identical.
  • Round 3: Gated on batch size, but vLLM's dynamic batch size changes every iteration. Setting a threshold based on observed max was unreachable — another gate that never triggered.
Lessons extracted:
  • Never use remote metrics for real-time admission — use local state
  • Gate metric must match the actual bottleneck
  • Gate threshold must be reachable under test load
  • Need Pareto sweep across multiple configurations, not single-point comparisons

Redesigned Approach

Built a local AdmissionTracker that maintains per-request resource estimates without any network calls. Three strategy families were defined:

StrategyMechanismParameters Swept
STATIC No gate. Controls concurrency only via vLLM's --max-num-seqs (prefetch count). prefetch = 1, 2, 3, 5, 8, 10, 15, 20
REACTIVE Checks current system utilization against a threshold before admitting. Retries with backoff on NACK. threshold = 0.50, 0.60, 0.70, 0.80, 0.90
PREDICTIVE Estimates per-request resource cost and admits only if remaining capacity suffices. threshold = 0.50, 0.60, 0.70, 0.80, 0.90

Strategy Commentary

Static wins because vLLM's scheduler IS the admission controller. With continuous batching, vLLM dynamically adjusts which requests get decode iterations each step. The prefetch parameter controls how many requests are queued at the engine level — with prefetch=3, the engine always has work ready without building up a backlog. The external admission gate adds nothing because it cannot influence the internal batch composition.
Reactive is broken: NACK churn creates a thundering-herd retry storm. All three reactive thresholds (0.50, 0.70, 0.90) generated 85,000–99,000 NACKs. The problem: decode throughput fluctuates naturally as requests start and finish. The gate reads a momentary dip, rejects the request, which retries 100ms later — only to find the same fluctuation. The short prompts (80% of traffic) accumulate massive queue wait times (45–65 seconds P95) while long/XL prompts that happen to arrive during a "good" moment sail through.
Predictive is too conservative: it NACKs all XL requests and starves the GPU. The predictive gate estimates each request's decode cost (output_tokens × tpot) and checks against remaining capacity. With threshold=0.60, long and XL requests exceed the budget — they are permanently rejected. Throughput drops to 37–53 tok/s because the GPU is partially idle while the gate blocks work.

Why Predictive Wins Here (and Only Here)

The KV cache is the scarce resource that predictive can model.

On 7B (Rounds A–C), decode bandwidth was the bottleneck. Every request shares it equally, and there's nothing an external gate can do — rejecting a request doesn't give more bandwidth to others.

On 14B, each request's KV cache footprint is quantifiable per-request: ~660 input tokens + 2048 output tokens = ~2,708 tokens of KV state. At 14B model size, this consumes a predictable amount of VRAM. The predictive gate can estimate this before admission and compare against the remaining KV budget.

At threshold=0.50, the gate admits requests until 50% of estimated KV capacity is reserved. This keeps 2–3 XL requests running concurrently — enough for decent throughput (22.7 tok/s) while preventing the preemption storms that cause TPOT to spike.
The Critical Difference
7B decodeShared resource (bandwidth) — can't reserve per-request
14B KV cachePer-request resource (VRAM) — can estimate and budget

This is the key insight: admission control only helps when the bottleneck resource can be attributed and budgeted per-request. Memory bandwidth is a shared pipe. KV cache is a per-request allocation.

AWS analogy: This is like the difference between scaling a CPU-bound service (adding more instances helps because CPU is per-request) vs scaling a network-I/O-bound service (adding instances doesn't help if they all share the same 10 Gbps VPC endpoint). The admission controller is the rate limiter at the VPC endpoint — it only helps when the bottleneck is something you can attribute per-connection.

9 Lessons Learned

1. On 7B, vLLM's Scheduler Is Sufficient

Across three metrics and 36 configurations on 7B AWQ, the answer was always the same: set prefetch=3 and let vLLM handle it. External admission control added complexity (reactive: 85–99K NACKs, predictive: 37–53 tok/s) without improving any metric. The engine's continuous batching scheduler already optimizes the shared bandwidth constraint.

Interview phrasing: "When the bottleneck is a shared resource like memory bandwidth, the scheduler inside the inference engine is better positioned than an external controller because it has direct visibility into the batch composition and can make per-iteration decisions."
2. On 14B with KV Pressure, Predictive Differentiates

When the model is large enough that KV cache becomes the binding constraint, predictive admission control finally earns its keep. At threshold=0.50, TPOT P95 stayed at 94.76ms (24% under SLA) while all static configs with comparable throughput exceeded the target. The key: KV cache is a per-request, budgetable resource unlike shared memory bandwidth.

Interview phrasing: "Admission control adds value when the scarce resource can be attributed per-request. KV cache has a known per-token footprint, so predictive gating can estimate whether admitting a request will cause preemption."
3. Metric Must Match the Actual Bottleneck

Three of four metrics (decode_throughput, gpu_compute, compound) were irrelevant on 7B because the real bottleneck was memory bandwidth — which none of them measured directly. GPU compute was always 0% because prefill completes instantly on small models. Compound = max(0%, decode%) just degrades to decode. Only kv_cache on 14B actually measured the binding constraint.

AWS analogy: This is like scaling on CPU utilization when the bottleneck is network I/O. The scaling policy fires (or doesn't), but it's measuring the wrong thing. You need to identify the binding constraint first, then instrument for that specific metric.
4. Predictive Needs Time-Weighted Modeling

On 7B, predictive was consistently too conservative (37–53 tok/s vs 86+ tok/s for static). The cost model estimates output_tokens × time_per_token as a static reservation, but decode throughput per token decreases as batch size grows. The model overestimates how long each request holds resources because it doesn't account for the shared-bandwidth effect. A time-weighted model that decays reservation as tokens complete would be more accurate.

5. Model Size Changes Optimal Prefetch

On 7B, optimal prefetch = 3 (enough concurrency to prevent head-of-line blocking, not so much that bandwidth is diluted). On 14B, optimal prefetch = 5 (enough to keep the GPU busy, but static pf=8 already exceeds SLA at 130ms TPOT). Larger models need lower concurrency because each request's KV cache footprint is proportionally larger. The right prefetch is a function of model_kv_size_per_token × avg_sequence_length / available_vram.

6. The Pareto Sweep Is the Methodology

Rather than picking one configuration and running it, sweeping the parameter space systematically reveals the Pareto frontier — the set of configurations where you can't improve one metric without worsening another. This is the same principle as load testing with graduated ramps: you want to see the system's behavior across its operating range, not just at one point. 39 configurations across 4 rounds, automated with a single sweep script.
