Phase 1 — Queue-Based Inference on EKS

Qwen2.5-7B-AWQ on NVIDIA T4 (g4dn.xlarge Spot) • Single worker • 2026-04-03

What Is This Experiment?

In Stage 2, we ran vLLM as a bare Docker container on a single EC2 g4dn.xlarge instance. Clients hit vLLM directly — no queue, no orchestration. It worked great at low concurrency, but at N=15+ it hit preemption storms (GPU memory exhausted, vLLM evicts and reprocesses requests) and risked OOM crashes. There was no way to absorb a traffic burst or scale to more GPUs.

Phase 1 moves to a production architecture: async queue-based serving on Kubernetes (EKS). Instead of hitting vLLM directly, requests flow through a pipeline:

RabbitMQ = durable job queue. Holds requests until a GPU worker has capacity. If a worker dies, the job redelivers automatically.
Redis pub/sub = real-time token relay. Each job gets its own channel. As the GPU generates tokens one by one, the worker publishes each to Redis, the gateway picks them up and streams them to the client instantly. Fire-and-forget, sub-millisecond.

The question this experiment answers: What does the queue add in overhead, and what does it give us in return?

Stage 2 — Direct Access (Before)
  • Client → vLLM directly (HTTP)
  • No buffering — GPU handles all requests immediately
  • Works at N=5, crashes/degrades at N=15
  • No scaling signal, no path to multi-GPU
  • Spot reclamation = request lost
Phase 1 — Queue-Based (After)
  • Client → API Gateway → RabbitMQ → Worker → vLLM
  • Queue absorbs bursts — GPU processes at its own pace
  • Works at N=5 AND N=15 (0 failures)
  • Queue depth = autoscaling signal for Phase 2
  • Spot reclamation = RabbitMQ redelivers unACK'd jobs

Infrastructure: EKS 1.29 cluster, 2x t3.medium CPU nodes (system pods), 1x g4dn.xlarge Spot GPU node (Karpenter-provisioned), all in private subnets with NAT Gateway. Total cost: ~$0.45/hr while running.

Test design: Three targeted rounds — N=1 (baseline overhead), N=5 (within worker capacity), N=15 (queue saturation). Each uses the same short/medium/long prompt mix from Stage 2 for apples-to-apples comparison. We measure two classes of metrics: server-side (measured inside the worker, no network noise) and client-side (end-to-end including port-forward latency).

How to read this: Each bar starts at t=0 (when the request was submitted). Red = sitting in RabbitMQ waiting for a prefetch slot. Yellow = prefill on GPU. Green = decoding tokens. Batch labels show when and why each group was dequeued. Notice S#3 and S#4 (Batch 2) finish completely before L#13 and M#7 begin their prefill — that's the ACK freeing the prefetch slot.
Why do long requests finish last? Two factors compound: (1) Queue ordering — the test fires 15 threads concurrently from [S*5, M*5, L*5], but enqueue order is non-deterministic (thread scheduling race). Batch 1 ended up as [S,S,S,M,M] not [S,S,S,S,S]. Longs tend to enqueue later (higher array indices = later thread start), but it's a race, not strict FIFO. (2) Slot recycling — shorts complete in ~1s freeing prefetch slots, while longs hold slots for ~10s. To isolate pure vLLM scheduling behavior from queue ordering, we'd need to randomize the prompt order in the test array.

Why does per-request throughput drop from 32→28 at N=15? It's not about having 15 requests in the system — the worker still runs 5 at a time. The drop happens because later batches have more long prompts, and long prompts have larger KV caches. Larger KV caches = more memory bandwidth consumed per decode step = each step takes longer for everyone in the batch.

Think of vLLM's decode step like a city bus: with 5 passengers going to nearby stops (short prompts, small KV), the bus moves fast. With 5 passengers going across town (long prompts, big KV), each stop takes longer because the bus has to navigate more memory to read each passenger's state. The bus (GPU) is equally busy in both cases — it's the per-stop cost that changes.

Stage 2 vs Stage 3 gap (44 vs 33 tok/s): Two config differences, not architecture overhead:

1. --enforce-eager (~5-10% hit): By default, vLLM compiles CUDA graphs at startup — it pre-records the exact GPU operation sequence for common batch sizes and "replays" them during inference, skipping the Python→CUDA kernel launch overhead per decode step. Like a pre-compiled stored procedure vs interpreting SQL every call. On T4 (16GB), this compilation temporarily allocates 1-3GB extra memory. With our 5.2GB model already loaded, the spike caused OOMKilled. --enforce-eager disables this — every decode step goes through full dynamic dispatch. Per-step latency: ~0.5ms (CUDA graph replay) → ~1-2ms (eager).

2. gpu_memory_utilization 0.85 vs 0.95 (minor): Lower utilization = fewer KV cache blocks allocated. Stage 2's 0.95 gave ~14.4GB for KV cache. Stage 3's 0.85 gives ~12.8GB — enough for 5 concurrent, but ~10% fewer total blocks available.

The Key Insight

The queue doesn't make inference faster — it makes overload survivable.

Stage 2 at N=15: vLLM tries to process all 15 simultaneously → KV cache exhausted → preemption cascade → latency spikes or OOM crash.

Stage 3 at N=15: worker takes 5 at a time, remaining 10 wait safely in RabbitMQ. Queue depth grows → KEDA triggers → Karpenter launches a second g4dn.xlarge → both workers drain the queue in parallel → queue_wait drops from 12s to <2s.

The queue is the backpressure mechanism that turns "crash under load" into "scale under load."
