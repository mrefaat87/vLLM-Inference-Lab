Phase 3 v3 — Backpressure Strategy Comparison

Pareto-distributed workloads • SLA targets • Cost-per-token • Separate EKS cluster (inference-phase3) • Qwen2.5-7B-AWQ on T4 • 2026-04-05

What Changed in v3?

External review identified four gaps in v1/v2: the "static wins" conclusion was an artifact of underload, workloads lacked realistic size distributions, there was no SLA objective function, and no cost tracking. This v3 redesign addresses all four.

Problems in v1/v2
  • KV cache never exceeded 25% — admission gates never fired
  • Uniform workloads hid scheduling pathologies
  • No SLA target — couldn't define "best" strategy
  • No $/token — couldn't connect strategy to cost
v3 Fixes
  • very_long (XL) prompt: ~1000 input + 2048 output = 1.22GB KV per request
  • Pareto distribution: 80% short, 15% medium, 4% long, 1% XL (random, seeded)
  • SLA targets: short <5s, medium <15s, long <30s, XL <90s P99 complete time
  • $/1M tokens: cost computed from GPU-hours during steady-state

Infrastructure: Separate EKS cluster (inference-phase3) with its own VPC (10.1.0.0/16) to avoid touching the Phase 4 production cluster. Shared ECR repos and S3 model cache. KEDA paused during experiment.

Threshold's failure mode at pareto_heavy is instructive. With 43 errors out of 108 requests (40% failure rate), threshold's /metrics polling overhead serializes admission under load. When the GPU is near capacity, each request pays ~2-5ms for the metrics check. With 10 concurrent prefetched messages, that's 20-50ms of serialized polling — during which new requests pile up. The cascade turns a manageable load into a timeout spiral. Meanwhile, static (no polling) and per-request (fast estimation, no HTTP call when running_requests is low) both handle 100% cleanly.

Strategy Verdicts

Static — Best for This Hardware

Static is the clear winner for a T4 running a 7B AWQ model. 100% SLA compliance on 3 of 4 workloads. Lowest or tied-lowest cost everywhere. Zero overhead from metrics polling or cost estimation. The GPU handles continuous batching internally — the worker's job is just to feed it requests as fast as possible.

When it fails: kv_stress (0% SLA) — but ALL strategies fail there. The T4 simply can't generate 2048 tokens per request at 0.5 req/s fast enough. This is a hardware limitation, not a strategy limitation.

Threshold — Actively Harmful at This Scale

Threshold is the worst strategy by every metric. 57% SLA at pareto_heavy (vs 100% for static and per-request). Complete failure at kv_stress and burst_outlier. 2.8x higher cost per token at pareto_heavy. The /metrics polling overhead that was meant to protect the GPU instead causes cascading timeouts under load. The irony: the strategy designed to prevent overload is the one that creates it.

Root cause: Each admission check makes an HTTP request to vLLM's /metrics endpoint (~2-5ms). With prefetch_count=10, up to 10 requests make this check concurrently. Under load, the serialized polling creates a 20-50ms admission window where no requests are processed — long enough for the queue to grow, causing more polling, causing more queue growth. A textbook positive feedback loop.

Per-Request — Same as Static (Estimation Never Triggers)

Per-request matches static on completion rate and cost, but fails SLA at burst_outlier. The KV cost estimation (prompt_length/4 + max_tokens) × 401KB never projected a value above the 80% threshold — the T4's 9.6GB KV cache is simply too large for a 7B model's requests. The estimation math is correct but the hardware has too much headroom. The strategy adds computation without benefit on this hardware.

The burst_outlier failure is interesting: all 90 requests complete (100% completion), but queue wait for requests submitted after XL bursts reaches 113 seconds. The strategy admits the XL burst because projected KV is below 80%, but the GPU takes so long to generate 2048 tokens per XL that the queue builds up. Static has the same queue buildup but its TTFT p99 is only 2.65s (vs per-request's 118.4s) — suggesting the per-request estimation overhead adds a delay that compounds during the burst.

The Real Lesson — Match the Gate to the Bottleneck

Strategy Match Matrix
BottleneckBest StrategyWhyExample
Decode throughput
(memory BW limited)		 Static No overhead. GPU's continuous batcher handles scheduling. Adding admission checks only creates delay. 7B model on T4 (this experiment)
KV cache memory
(VRAM limited)		 Per-Request Cost estimation prevents preemption storms. A 32K-context request should be deferred when KV is at 70%. 70B model on A100, long contexts
Both scarce
(capacity-constrained fleet)		 Threshold Adapts to runtime state without estimation error. Best pragmatic middle ground when you can't predict request cost. Multi-model serving, variable traffic
For an Anthropic engineering interview: The takeaway isn't "static is best" — it's that the optimal admission strategy depends on which resource is the binding constraint. Knowing how to identify the bottleneck (KV cache vs decode throughput vs prefill compute) and match the admission gate to it is the skill. A system that gates on the wrong metric adds complexity and cost without benefit.
