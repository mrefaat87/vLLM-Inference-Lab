FSR economics: $0.75/hr/AZ flat cost. Each cold-start saves 346s vs Hub. Break-even at ~10 cold-starts/hr/AZ in saved cold-start seconds (≈$0.0002/saved-second). For a Tier-0 inference platform where P99 cold-start is user-visible, FSR is a no-brainer. For dev clusters, it's pure waste.
* Footnote on image_download / image_unpack for prebaked variants (C, D): The image bytes are already in containerd's local cache on the AMI — there is no network pull and no layer decompression happening. The 1-3s reported as image_download is containerd resolving the local image reference and verifying manifests in response to kubelet's PullImage CRI call. The ~50-120ms reported as image_unpack is the per-container overlayfs snapshot creation (mkdir for the writable layer, lowerdir/upperdir/workdir setup) — work that happens on every container start regardless of whether the image is cached. Stage labels are kept consistent across variants so the journal-event timing aligns; the semantic meaning shifts from "real pull + unpack" (variants A, B) to "local lookup + snapshot create" (variants C, D). The actual win in D isn't "0ms unpack" — it's that 290s of network + decompression is replaced by 1.3s of local containerd work.

Also note: for variants A and B, containerd v1.7 streams unpack concurrent with download — so the ~50ms shown as image_unpack there is also not the real ~76s of decompression. That work happens in parallel during image_download. The ~50ms is just the trailing finalization between the last byte arriving and the PullImage RPC returning to kubelet.

Variant E — RunAI Model Streamer: what we found

Variant E swaps the aws s3 cp init container + standard vLLM weight loader for the RunAI Model Streamer (--load-format=runai_streamer --model=s3://…/). The streamer fetches safetensors directly from S3 to a CPU pinned buffer and copies to GPU — never touching disk. New AMI: ami-099f89419c0973f5b with the streamer-augmented vLLM image baked in.

The fused fetch+load picture

model_download_s3 structurally disappears (no init container). Its old time is fused into weight_load_gpu_mem. So D and E should be compared by the SUM of those two stages:

Variant model_download_s3 weight_load_gpu_mem Fused total
D: Prebake + FSR (init container + FSR-warm disk read) 37s 4.6s 41.6s
E: Streamer + FSR (S3→CPU pinned→GPU, no disk hop) 0s (absorbed) 66.1s 66.1s
Δ E vs D (on the fused pair) −37s +61.5s +24.5s SLOWER
Counter-intuitive result: the streamer is slower on the fused fetch+load by 24.5s. The vendor's "3-5× speedup" claim is over a NAIVE pipeline (S3 cp to disk → re-read from disk → copy to GPU). Variant D wasn't naive: FSR pre-warmed the gp3 root volume to memory-bandwidth speeds, so the disk read was nearly free (4.6s for 4.5GB ≈ 1 GB/s). The streamer's ceiling is single-instance S3 read throughput, ~70 MB/s sustained on g4dn.xlarge in us-east-1a — well below FSR-warm gp3.

Where E's 30s win actually came from

E is still 30s faster overall (212s vs D's 242s). But that saving is NOT in the model load — it's in the side-effects of removing the init container entirely:

  • No init→main K8s/CRI handoff — kubelet doesn't pause to clean up the model-download container, mount its emptyDir read-only into the main container, swap PIDs, etc. That handoff is on the order of tens of seconds with our pre-v3 probes (initialDelaySeconds=120 starts counting after main container creation, not pod creation).
  • Slightly faster vllm_init_cuda_ctx — 20.3s vs D's 23s. The mount tree is simpler (no /models volumeMount), and there's less filesystem warmup work for vLLM's first-touch reads on the streamer-baked AMI.
  • Bootstrap and cuda_graph_warmup are unchanged — the AMI structure is the same, FSR pre-warm covers the same blocks.

Tail-risk surprise: FSR pre-warm isn't deterministic

Run 2 of E hit 545s — bootstrap and vllm_init both 3× the other two runs. Same AMI, AZ, instance type. Variant D's three runs were stable; E's third run is more sensitive to partial-pre-warm volumes because the streamer competes for memory bandwidth with first-touch EBS reads.

Operability lesson for Phase 7: FSR pre-warm is best-effort, not a guarantee. AWS docs describe it with a per-AZ-per-snapshot rate ceiling, and in practice some volumes get served from non-pre-warmed shards. Median (212s) is the typical case; the range (210.6s–545.4s) is the tail risk. A small percentage of cold starts will spike — design fallback paths (priority retry, multi-AZ FSR, warm pool) accordingly.

Decision-tree update for Phase 5+

Streaming model loaders are not a free win once you already have FSR. Use the streamer when:

  • You can't afford FSR's $0.75/hr/AZ but want fast model load
  • You're scaling horizontally enough that single-instance S3 bandwidth becomes shared/limiting (multiple workers reading the same model concurrently)
  • You're bouncing models often — a single pre-baked AMI can't fit N models, so the streamer + FSR-warmed root volume is the cheapest cache miss

Skip the streamer when FSR is already paid for and the workload is single-tenant on one model.

What we'd try next to actually beat D

  • Tune RUNAI_STREAMER_* env vars for parallel S3 streams — defaults appear conservative
  • Pre-shard AWQ weights into more safetensors files — the streamer can't parallelize what isn't sharded
  • Try the existing v0.19.0-slim-streamer image (4GB instead of 9.5GB) — smaller bootstrap exposes the streamer benefit better
  • Benchmark vs Tensorizer (CoreWeave) — single .tensors file sidesteps the AWQ-shard parallelism limit

Variant F — Pre-warmed JIT compile caches: what we found

Per COLD_START_RESEARCH.md §R2.1a (Doubleword Q1-2026 finding), vLLM's vllm_init_cuda_ctx is supposed to be dominated by JIT compilers — torch.compile, Triton, FlashInfer, and vLLM's own FX cache — not by Python imports or CUDA context init. The hypothesis: run vLLM once during AMI build, snapshot all four caches into /opt/vllm-cache/, bind-mount that hostPath at the same absolute path at runtime (cache keys embed paths), and the stage should drop by 5-15s. New AMI: ami-07a89172fa00c8e0f with the JIT caches baked in alongside the stock 9.5GB vLLM image.

The pre-warmed cache appears to dampen FSR's per-shard variance — possibly because fewer first-touch reads on cold EBS blocks happen during the JIT phase (the file system prefetches the cache dir during the model-download init container, while the gp3 volume is being warmed in parallel). This is a tail-risk reduction, not a typical-case win.

Two operational gotchas worth recording

  1. ctr run --rm -d is invalid. Unlike Docker, containerd's ctr CLI rejects --rm together with -d. Fix: drop --rm, manually ctr containers rm after killing the task. Cost one full AMI build (~$0.05).
  2. readOnly: true on the cache hostPath crashes torch.compile. Even when only reading a cached entry, torchinductor writes a .<hash>.tmp for atomic-rename. A read-only mount returns [Errno 30] Read-only file system, vLLM logs "Compiling model again due to a load failure", and on the next write attempt crashes outright with an unhandled OSError. The cache is per-node hostPath with no AMI persistence anyway — pod-side writes vanish at node consolidation — so readOnly: false is correct and risk-free.

Why the predicted save didn't materialize — three hypotheses

  • vLLM 0.19's torch.compile path is mostly downstream of vllm_init_cuda_ctx. Cache hits in that phase don't surface in the stage the harness measures. The 32s "engine setup + KV cache sizing + graph build" gap between cuda_context_ready and weight_load_start in the smoke trace is where torch.compile likely fires — invisible to the current decomposition.
  • The 31 MB cache is small relative to expectations. Doubleword's "10-20s save" was measured on B200 + MoE + newer SGLang where FlashInfer + Triton + TVM-FFI all JIT meaningfully. On vLLM 0.19 + T4 + AWQ the addressable surface is just torch + triton (~31 MB). A realistic ceiling here is closer to 2-5s, not 10-15s.
  • vLLM 0.19 is the wrong vLLM. The Round-2 research explicitly flagged "vLLM 0.19 may under-represent achievable savings; pin newer vLLM to access full multi-cache surface area." Re-running F on vLLM ≥0.7 (Q1-2026 release with first-class cache persistence APIs) is a deliberate Phase 5 follow-up.

Decision-tree update for Phase 5+

Pre-baking JIT compile caches (variant F) gives a small total-time improvement (~20s median) and a large variance reduction (24×) on vLLM 0.19. Use it when production cold-start SLOs care about p99, not p50. Don't use it expecting vllm_init_cuda_ctx to shrink — that bet didn't pay out on this engine version.

For the next material reduction in vllm_init, the fastest paths are:

  • Upgrade to vLLM ≥0.7 with first-class cache persistence and re-run F
  • Attack Python import time directly (lazy imports, vLLM monkey-patches) — much higher blast radius
  • Snapshot/restore (Phase 6, blocked on EKS GPU AMI shipping driver 580+ — current AMI ships 570.195.03, close but not there)

Three operational gotchas worth recording

  1. Karpenter node role has no S3 perms. First build failed at the aws s3 cp provisioner with AccessDenied: ListBucket. The Packer build host inherits the inference-phase4-1-karpenter-node instance profile, which has only ECR-ReadOnly + EKS worker policies. D's runtime init container works because the pod's ServiceAccount uses IRSA mapped to a different role with S3 read. Fix matches the ECR-push pattern: temp inline policy TempVariantGModelCacheRead (s3:GetObject + s3:ListBucket on the model bucket), build, detach immediately. Do not add this permanently — every GPU node would inherit the perm.
  2. Packer's AMI-ready wait timed out at 41:47. The 120 GiB volume + ~20 GiB of data made the snapshot slow enough that Packer gave up before AWS finished registering the AMI. Critically: the AMI did register, the snapshot did complete — Packer's "cleanup" only terminated the source EC2 instance and the keypair. Tags were never applied. Fix: wait for state=available, then aws ec2 create-tags --resources <ami> <snap> --tags ... with the same tag set the Packer template specifies. (Memory feedback_packer_ami_wait_timeout.md warned about this; reconfirmed.)
  3. Packer 1.11.2 + HCL2: {{timestamp}} doesn't interpolate in ami_name. The AMI's Name attribute came out as a random string (nu2QeU1) instead of inference-lab-gpu-node-model-baked-1746245682. Doesn't break the experiment because Karpenter selects on the Variant tag, but worth switching to ${formatdate("YYYYMMDDhhmmss", timestamp())} in future templates.

Decision-tree update for Phase 5+

Variant G ties D on median latency (241s) and dramatically reduces variance (19× tighter stddev). Pick G over D when p99 matters more than ops simplicity. Pick F over G when minimum median matters AND the model lifecycle can be separated from the AMI lifecycle. Pick D over G when the model rotates often enough that rebuilding+FSR-rewarming the AMI per model change is unaffordable.

For the next material reduction in cold-start time on this stack, the actual disk read ceiling is now exposed (Variant G makes it visible). The fastest paths from here:

  • Pin model in tmpfs on node bootstrap — but g4dn.xlarge has only 16 GiB RAM, vLLM uses ~12 GiB GPU + ~4 GiB CPU; would clash on this instance. Viable on bigger nodes.
  • Use S3 CSI Mountpoint as a read-through cache — vLLM reads weights through a FUSE mount that streams from S3 on first miss; the kernel page-caches FUSE reads. Sidesteps both the gp3 disk read and the streamer S3-throughput ceiling. Untested; Phase 5 candidate.
  • CUDA snapshot/restore (Phase 6) — skips vllm_init_cuda_ctx + weight_load_gpu_mem entirely by snapshotting a warm process. Blocked on EKS GPU AMI shipping driver 580+.

Variant H — FSx for Lustre shared model cache (NIMCache pattern): what we found

Variant G ties D on median latency but couples model identity to AMI identity — every model swap requires an AMI rebake plus FSR re-warm. NVIDIA NIM's NIMCache pattern uses a shared FSx for Lustre filesystem mounted into every inference pod via PVC; model swaps become PVC-path changes. The bet: Lustre reads on a single g4dn.xlarge match or beat FSR-warmed gp3, the FSx CSI mount overhead is small, and Lustre is deterministic.

What changed structurally vs Variant G

  • Same stock vLLM image as D/G — no streamer needed; vLLM's standard weight loader handles the FSx mount as ordinary local-disk-style I/O.
  • New Packer template packer/lustre-client/gpu-node-lustre.pkr.hcl: stock prebake template + amazon-linux-extras enable lustre && yum install -y lustre-client. Module ships in the AMI; /etc/modules-load.d/lustre.conf auto-loads at every boot. ami-0002c079b74300348, FSR enabled in us-east-1a for the measurement window.
  • New Terraform terraform/fsx.tf: aws_fsx_lustre_file_system SCRATCH_2 SSD, 1.2 TiB minimum, single-AZ in us-east-1a. Dedicated SG with port 988 + 1018-1023 ingress from the EKS node SG and self-referential rules (FSx pre-flight requires self-ingress on these ports — first deploy failed with InvalidNetworkSettings until added). Tagged experiment=phase4.1-variantH, auto-delete=true.
  • FSx CSI driver Helm-installed into kube-system; new IRSA role inference-phase4-1-fsx-csi-driver. Distinct from the EBS-CSI IRSA already on the cluster.
  • Static PV model-weights-fsx-pv bound by name to PVC model-weights-fsx (RWX). One-time K8s Job fsx-populate copies weights from S3 to /mnt/fsx/qwen2.5-7b-awq (runs on H GPU pool — the only nodes with the lustre kernel module).
  • New manifest baseline-pod-fsx-weights.yaml: zero init containers, PVC mounted RO at /mnt/fsx, --model=/mnt/fsx/qwen2.5-7b-awq.
  • New Karpenter NodePool gpu-pool-prebaked-fsx with matching image-source=prebaked-fsx label. Same g4dn.xlarge / Spot / us-east-1a as D/G.

1. Lustre reads beat FSR-warmed gp3 by ~3.5×. G's 44.4s reflects vLLM as the first reader on FSR-warmed gp3 (~110 MB/s effective on g4dn.xlarge). The 12.6s number is close to PCIe-bound for transferring 4.5 GB across the network into GPU memory — storage is no longer the bottleneck. SCRATCH_2 SSD's per-client throughput on a single g4dn.xlarge was the open question of this variant; the answer is "more than enough."
2. The fair-sum comparison flips the per-stage narrative. Per the rule G established (don't compare per-stage across architectures with different init container patterns), look at (model_download_s3 + weight_load_gpu_mem): D = 41.6s, G = 44.4s, H ≈ 13s + the implicit FSx CSI mount (~10-15s in the Scheduled→Pulled gap). Even with a generous 15s mount estimate, H ties or beats both D and G on the storage-layer fair sum. Lustre is doing real work.
3. Variance is great, but bigger than F/G. H stddev = 9.4s — tighter than D's 119.6s, looser than F's 5.0s and G's 6.3s. The driver of H's spread is node_bootstrap (45–54s, stddev 4.6s, FSR-bound; same partial-warm sensitivity as D/E). Lustre itself was deterministic: weight_load_gpu_mem 12.5 / 12.6 / 13.2 across three runs — stddev 0.36s, the only sub-1s-stddev stage in the entire experiment.
4. The FSR partial-warm trap is real and bit us once. The first attempted h-001 fired 20 seconds after FSR EnabledTime and totaled 413s — classic partial-FSR profile (node_bootstrap=89s, vllm_init=71s — same shape as variant C). Re-running 12 minutes later: 228.6s. Operational rule: wait at least 5–10 minutes after FSR enables before the first measurement; AWS's "best effort" pre-warm doesn't credit the first volume creations. The cold result is preserved at tests/baseline_runs/h-001-fsrcold.json for future audit.
5. Why H supersedes D as the multi-model recommendation. D was the only A–G variant that decoupled model identity from AMI identity, but it paid 37s for an init-container fetch. H removes the init container, mounts a shared FSx Lustre filesystem via PVC, and lands at 214.5s — faster than D and structurally fits the multi-model lifecycle (model swap = PVC path change, not AMI rebuild). At N=4 models × M=2 AZs, H costs $0.48/hr total (one filesystem per AZ, all models inside) vs the FSR-per-snapshot pattern's $6.00/hr.

Anatomy of a cold start — from scale-up trigger to first token

A complete walk through the journey, with the actors, what they're doing, and where time goes. Phase numbers (T+Xs..T+Ys) below are for variant D (Prebake + FSR — total 242s) unless noted otherwise. Stage colors match the waterfall legend (provisioning, container image, model weights, framework, readiness).

The 8 actors

KarpenterEKS-side autoscaler. Watches Pending pods, picks NodePools, creates NodeClaim → calls EC2 RunInstances.
EC2 control planeAllocates Spot capacity, launches the instance, attaches the EBS volume, returns instance-id once "running".
EBS + S3 (snapshot store)EBS volume restored from AMI snapshot is metadata-only at first; blocks lazy-fetch from S3 on first read. FSR pre-warms.
Linux kernel + systemdBoots from the EBS root volume. Runs networking, kubelet, containerd as services.
kubeletJoins the cluster (EKS bootstrap.sh), reports NodeReady=True, schedules pods, reads imagePullPolicy and triggers image pulls via CRI.
containerd + overlayfsPulls images, decompresses layers (concurrent with download), creates per-container snapshots (lowerdir/upperdir/workdir).
aws-cli init containerDownloads model weights from S3 to an emptyDir on the gp3 root volume. Init runs to completion before main container starts.
vLLM + GPUImports torch + CUDA runtime, creates CUDA context, loads weights to GPU memory, captures CUDA graphs, opens HTTP /health.

Actor timeline (variant D, ~242s total)

Each row is one actor; each bar marks when that actor is the bottleneck. Hover any bar for the duration. Note that the kernel+kubelet boot (46s) and the init container (37s) run sequentially, not concurrently — kubelet has to be Ready before the pod gets scheduled.

The 13 phases of a cold start

PHASE 0Scale-up triggerT=0
A scaler (KEDA / HPA / manual) decides to spawn a pod. The pod lands in Pending state because no node currently has GPU capacity. This is t=0 of cold start. Phase 4.1's harness uses a manual kubectl apply to trigger this; production would have KEDA reading queue depth or HPA reading custom metrics.
PHASE 1Karpenter sees the pending pod and decides where it goesT+0..1s
Actors: Karpenter. Stage: karpenter_scheduling. Karpenter watches unscheduledPods, evaluates each NodePool's template requirements (instance-type, capacity-type, AZ, taints) against the pod's nodeSelector + tolerations, picks a winner, creates a NodeClaim resource. This is where our Phase 4.1 routing bug bit: both gpu-pool and gpu-pool-prebaked matched node-role: gpu, and Karpenter picked nondeterministically. Fix: distinct labels per NodePool template and explicit nodeSelector per variant.
PHASE 2EC2 Spot fulfillment — instance launchesT+1..3s
Actors: Karpenter, EC2 control plane, Spot capacity pool. Stage: ec2_spot_fulfillment. Karpenter calls RunInstances with a Spot fleet config. AWS searches Spot capacity in the AZ (us-east-1a here), launches the instance, returns instance-id once "running." Healthy day: 2-5s. Spot-exhausted day: minutes or capacity errors — falls outside this experiment.
PHASE 3EBS volume restore + OS boot — the lazy-load chapterT+3..49s
Actors: EC2, EBS, S3 (snapshot store), Linux kernel. Stage: node_bootstrap (continues into phase 4). The EBS root volume is "restored from" the AMI's snapshot but is metadata-only at first. Every block read triggers either a fetch from S3 (lazy-load: ~10-50ms per block) or a warm read (FSR pre-warmed: normal SSD speed). The kernel boots from the volume — kernel bytes themselves are first-touch reads.

Variant C without FSR pays this tax (+115s vs Hub) over the entire OS boot + containerd image-cache scan. Variant D with FSR doesn't.
PHASE 4Node joins the cluster (NodeReady=True)T+30..49s
Actors: kubelet, EKS control plane, Karpenter. The kubelet runs the EKS bootstrap.sh, calls EKS API, downloads CA certs, posts NodeReady=True. Karpenter applies NodeClaim labels (including our image-source: prebaked-stock label) so the pod's nodeSelector resolves correctly.
PHASE 5Pod scheduled to the new nodeT+49..50s
Actors: kube-scheduler. Pod's nodeSelector + tolerations match the new node's labels + taints, so kube-scheduler binds the pod. Pause container (pod sandbox) is created — sets up cgroups, network namespace. Sub-second.
PHASE 6Init container — model weights download from S3T+50..87s
Actors: aws-cli, S3, gp3 EBS. Stage: model_download_s3. aws s3 cp --recursive pulls 4.5GB of Qwen2.5-7B-AWQ weights into an emptyDir on the gp3 root volume. Bottleneck is gp3 write throughput (125 MB/s baseline) — same gotcha as image unpack. 4.5GB / 125 MB/s ≈ 36s minimum, matching our measurement. Optimization candidates: replace with a streaming model loader (RunAI Model Streamer, Tensorizer) that pipelines decode → GPU copy.
PHASE 7Image pull / lookup (semantic varies by variant)T+87..88s
Actors: kubelet (CRI), containerd. Stage: image_download. kubelet calls containerd's PullImage CRI method. Behavior splits by variant:
  • A (Hub) / B (ECR): network pull. containerd downloads layers in parallel and decompresses to overlayfs concurrently. Bottleneck is gp3 unpack rate, NOT network bandwidth — registry locality buys ~5s, not 100s.
  • C / D (Prebake): local lookup. Image already in containerd cache. ~1-3s for manifest verification + (in C's case) first-touch reads of layer files (lazy-load tax). With FSR (D), no tax.
PHASE 8Per-container overlayfs snapshot creationT+88s..T+88.06s
Actors: containerd, overlayfs. Stage: image_unpack (~50-120ms). NOT actually unpacking the image — for prebakes, the image bytes are already cached. This is containerd creating a fresh writable layer for THIS container instance: mkdir for upperdir/workdir, set up the overlayfs lowerdir/upperdir/workdir mount triplet. Same work happens on every container start regardless of cache state. For network pulls (A/B), the trailing 50ms is just the CRI handshake completing — real decompression already streamed concurrent with download in Phase 7.
PHASE 9vLLM process startup + CUDA context initT+88..111s
Actors: runc, Python interpreter, vLLM, NVIDIA driver, CUDA runtime. Stage: vllm_init_cuda_ctx. runc creates the main container; Python interpreter spins up; vLLM imports the dependency tree (torch, transformers, flash-attn, CUDA runtime libs). First CUDA op creates the CUDA context on the GPU — single-digit-s call. Variant C's tax here (+123s vs Hub): torch + CUDA libs are first-touch-read from EBS, the heaviest part of the lazy-load tax. Variant D (FSR) is ~23s; could fall to ~10-12s if torch.compile / CUDA kernel caches are pre-warmed and baked into the AMI.
PHASE 10Weight load to GPU memoryT+111..115.6s
Actors: vLLM safetensors loader, gp3 EBS, GPU PCIe bus. Stage: weight_load_gpu_mem. vLLM reads the AWQ-quantized weights from emptyDir and copies them to GPU VRAM. Variant D's huge saving here (4.6s vs 40s): FSR pre-warmed the WHOLE root volume, not just the prebaked image — so emptyDir reads are also hot. AWQ keeps weights in INT4 packed form; dequant happens on the fly during decode, so no startup-time decompression.
PHASE 11CUDA graph capture + warmupT+115.6..125.5s
Actors: vLLM, CUDA, GPU. Stage: cuda_graph_warmup. vLLM compiles CUDA graphs for each batch size in its capture set (default: 51 piecewise + 35 full graphs). A CUDA graph is a recorded sequence of GPU ops — replaying it is much faster than re-issuing each kernel launch. Cost: ~10s of capture time. Tradeoff: --enforce-eager skips this entirely (saves 10s) but tanks steady-state inference latency by ~15-20%. Better optimization: restrict capture sizes to a subset matching your traffic histogram via --cuda-graph-sizes.
PHASE 12Readiness probe pass — pod marked ReadyT+125.5..130.2s
Actors: vLLM HTTP server, kubelet probe loop. Stage: readiness_probe_pass. vLLM is now actually responding to /health. But probe lag depends on the spec — with our pre-v3 config (initialDelaySeconds=120, periodSeconds=10), we've already paid 120s of "wait silently" before the first probe. The 4.7s here is the probe-period lag between vLLM-actually-ready and the next probe firing. Switching to a startupProbe only helps once total cold start drops below the 120s initialDelaySeconds — which variant D achieves at 130s, so this is on the verge of being relevant.
PHASE 13First token served — request in, SSE byte outT+130.2..133.3s
Actors: Service endpoints, vLLM, GPU. Stage: first_token_served. Pod is Ready, kube-proxy updates Service endpoints, the smoke client makes a /v1/completions request. vLLM does prefill (encode the prompt → produce KV cache) and emits the first SSE byte. ~3s of TTFT for the smoke client's prompt — typical for Qwen2.5-7B at this batch size.

Four gotchas hidden in the journey

Gotcha 1 — EBS lazy-load: snapshots are stored in S3, not on the volume

An AMI is an EBS snapshot stored in S3 (managed, not in your buckets). When EC2 launches an instance from an AMI, the volume reports as "available" instantly — but blocks aren't actually copied yet. Each first read triggers a fetch from S3 (~10-50ms per block). FSR ($0.75/hr/AZ) pre-warms the snapshot in an AZ so first-reads are normal-speed.

This is invisible if you only watch image_download — the lazy-load tax shows up wherever the OS / kubelet / vLLM actually reads files: kernel boot, containerd config scan, vLLM's torch + CUDA imports, weight load. In our experiment, variant C without FSR paid +115s on node_bootstrap and +123s on vllm_init, completely erasing the 287s saved on image pull.

Gotcha 2 — gp3's 125 MB/s ceiling dominates everything image-related

gp3 EBS volumes have a baseline throughput of 125 MB/s, regardless of size. This is the limit on writes during image unpack (network pull → decompress → write to overlayfs) and reads during model load. For a 9.5GB compressed image that decompresses to ~30GB on disk:

unpacked image bytes ÷ gp3 throughput = ~30,000 MB ÷ 125 MB/s ≈ 240s
model weights (4.5GB) ÷ gp3 throughput = ~4,500 MB ÷ 125 MB/s ≈ 36s

The first explains why ECR same-region didn't beat Docker Hub for our 9.5GB image: both sides hit the gp3 unpack ceiling before the network pipe is saturated. The second explains why the init container takes ~37s. Tunable: gp3 supports up to 1000 MB/s for an extra ~$0.08/GB/month. Bigger lever: switch to NVMe instance store on g6/g6e (4-10 GB/s, ephemeral) — the Phase 5 instance-class question.

Gotcha 3 — NodePool routing nondeterminism

If two NodePools share a label (e.g., both have node-role: gpu) and a Pending pod has a nodeSelector that matches both, Karpenter picks one nondeterministically. Our first matrix run had this bug: variants A and B occasionally landed on prebaked nodes, contaminating the pull-time data.

The fix: every NodePool gets a unique discriminator label in its spec.template.metadata.labels (we used image-source: default-eks vs image-source: prebaked-stock), and every variant's pod manifest includes the matching nodeSelector. The pre-flight assertion in run_pull_comparison.py now refuses to run if a variant's manifest lacks its expected discriminator.

Gotcha 4 — "image_download" and "image_unpack" mean different things across variants

For variants A and B, image_download is a real network pull and image_unpack is the trailing 50ms after pull (real decompression streamed in parallel). For variants C and D, image_download is containerd resolving the local image reference (~1-3s), and image_unpack is the per-container overlayfs snapshot creation (~50-120ms) — neither involves network or decompression.

The semantic shift is invisible if you trust the stage labels at face value. The render's "stage_leak" assertion failed loudly precisely because variants have wildly different times for stages whose names suggest they should be invariant — surfacing the warm-vs-cold-EBS axis as a separate variable that needs explicit handling in future experiments.

Where this leaves us for Phase 5+: the FSR + prebake variant gives 242s total; variant E (streaming loader) brings it to 212s. The remaining reducible chunks are node_bootstrap (46s — Karpenter warm pool would erase this), vllm_init_cuda_ctx (~20s — pre-warmed compile cache), and the fused fetch+load (66s with the streamer; tunable via shard-count + concurrent-stream env vars). Each is an independent lever; combined, sub-130s cold start looks reachable.

Findings (revised through the 8-way comparison)

1. Registry locality is worth ~5s, not 100s, for big images. A and B differ only in image source (Hub vs ECR same-region). Pull times: 290s vs 295s. The bottleneck for a 9.5GB image is gp3 EBS unpack at ~125 MB/s (~76s minimum decompression), not network bandwidth. ECR mirroring is still worth doing for operational reasons (no Hub rate limits, no Hub outages, faster authn) — but it does not move the cold-start needle.
2. Pre-baking is a NET LOSS without FSR (+128s vs Hub). The S3-lazy-load tax does not show up in image_download (containerd just reads the local manifest in 2-3s). It shows up in node_bootstrap (+115s) and vllm_init_cuda_ctx (+123s) when the OS / kubelet / vLLM imports first-touch-read files from the unpacked image layers on the EBS snapshot. Each block: ~10-50ms first-read tax. Aggregated across vLLM's import tree, that's ~238s of regression.

The original render assertion was wrong to look only at stage 4. The right comparison is total scale-up-to-ready time, not any single stage.
3. FSR + prebake outperformed every prediction (242s total, -59% vs Hub). Predicted ~480s (closing the 238s lazy-load gap). Actual: 242s — almost half the prediction. FSR pre-warms the WHOLE root volume snapshot, not just the unpacked image layers — so it also benefits the gp3 slack space the model-download init container writes weights into. weight_load_gpu_mem dropped 40s → 4.6s, a stage I hadn't even modeled as FSR-relevant. node_bootstrap is also faster on prebaked AMI (46s) than on stock EKS AMI (64s) because the prebaked AMI carries containerd parallelism tuning (max_concurrent_downloads=10) that the upstream defaults don't.
4. FSx for Lustre is the multi-model production answer (Variant H, 214.5s). Lustre's per-client read throughput on a single g4dn.xlarge (~360 MB/s) crushes FSR-warmed gp3 at the same workload — weight_load_gpu_mem drops from G's 44.4s to 12.6s. H lands at 214.5s median with 9.4s stddev, faster than every prior variant. Cost shape inverts at multi-model scale: at N=4 models × M=2 AZs, H costs $0.48/hr vs FSR-per-snapshot's $6.00/hr. Phase 6 multi-model serving should default to H's storage layer.
Decision tree for cold-start optimization (revised through 8-way):
  1. Don't mirror to ECR for cold-start latency alone (gp3 unpack dominates network)
  2. Don't pre-bake without FSR (lazy-load tax exceeds pull savings)
  3. Pre-bake + FSR is the single-model production answer for big images on frequently-scaling clusters (D, F: 221–242s)
  4. FSx for Lustre PVC is the multi-model production answer (H: 214.5s, ~$0.48/hr at N=4 × M=2). Add weights to the FS, swap models by changing the mount path, no AMI rebuilds.
  5. Always wait ≥5–10 min after FSR EnabledTime before the first measurement — partial-warm volumes look identical to no-FSR launches and ruin one in a few runs (E run 2, H first attempt).
  6. Compare D / G / H by the SUM (model_download_s3 + weight_load_gpu_mem), not individual stages — D's preheat-via-init-container hides where the disk read actually happens.
