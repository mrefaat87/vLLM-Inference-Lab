What We Built (and Why This Experiment Exists)

Phases 1–3 of this project built and refined an inference pipeline on EKS: RabbitMQ for queuing, a Python worker that streams from a vLLM sidecar, Redis pub/sub for fan-out, and SSE for client delivery. Phase 2 added KEDA autoscaling that could grow from 1 to 4 GPU workers based on queue depth. Phase 3 proved that static admission control (just set a prefetch limit and let vLLM batch internally) beats per-request gating.

That left an open question: what signal should trigger adding more GPU workers?

Queue depth is the obvious choice — it's the GPU equivalent of SQS-based step scaling. But GPU inference has a property that CPU workloads don't: a single expensive request can saturate GPU memory (the KV cache) while barely moving the queue. The queue says "everything's fine." The GPU says "I'm out of memory."

Phase 4 tests whether adding a KV cache utilization signal alongside queue depth produces meaningfully better scaling outcomes — and under what conditions it matters.

The Four Policies

I tested two queue-only policies and two composite (queue + KV cache) policies:

A Queue-Only (threshold=5)
Scale when queue depth exceeds 5 per replica. Ignores GPU state entirely.
AWS analogy: SQS-based step scaling.
B Queue-Eager (threshold=3)
Same as A but reacts earlier at queue depth 3. Tests whether a lower threshold helps.
AWS analogy: Aggressive step scaling with low threshold.
C Composite Conservative (KV>80%)
Scale on queue depth or KV cache utilization above 80%. Sees GPU memory pressure even when the queue is short.
AWS analogy: Composite CloudWatch alarm (CPU or memory).
D Composite Aggressive (KV>65%)
Same as C but fires at 65% KV utilization — scales before rejection starts.
AWS analogy: Predictive scaling based on projected capacity.

The Workload

Real inference traffic follows a power-law distribution: most requests are cheap, but a few are enormous. I used a Pareto distribution: 80% short (~50 tokens), 15% medium (~200 tokens), 4% long (~800 tokens), and 1% XL (2048 output tokens, each consuming ~1.22GB of KV cache).

Seven graduated load phases, run identically for each policy:

Act 1: Under Normal Load, All Policies Are Identical

Through the first four phases (light → moderate → heavy → sustained), the four policies are virtually indistinguishable. All achieve 100% success rates. TTFT, throughput, and cost converge to the same values. Lowering the queue threshold from 5 to 3 (A vs B) makes almost no difference.

Act 2: KV Stress — Where the Policies Diverge

Then the workload shifts to all-XL requests at 0.5 req/s. Each request generates 2048 tokens, consuming ~1.22GB of KV cache. The request rate is low — the queue barely grows. But the GPU is saturated.

KV cache utilization crossed the threshold independently of queue depth. KEDA triggered a scale-up that queue-only policies would never trigger. Policy D (65% threshold) fired earliest: 100% success, 968 tok/s.

This is the scenario where composite triggers earn their complexity. The queue looks fine, but the GPU is internally thrashing — like a CPU-based SQS scaler that can't see that the worker's memory is full. Adding a KV cache alarm is like adding a memory-pressure CloudWatch alarm alongside SQS depth. Without it, you're flying blind to an entire class of saturation.

Act 3: Burst — The Cascading Payoff

Immediately after KV stress, the burst phase hits all policies with the same 45 requests (mixed sizes with periodic XL spikes at 1.0 req/s). The results are dramatic:

This is the insight that makes composite scaling worth the complexity: scaling decisions compound. The burst phase didn't trigger any new scaling — it benefited from scaling that happened in the previous phase. Composite policies made the right call earlier, and that carried forward.

What About Cost?

All four policies converge to $0.24–$0.25 per million tokens overall. The cost is dominated by GPU instance hours (g4dn.xlarge Spot at ~$0.16/hr), not by scaling policy.

The interesting outlier: during KV stress, composite policies are cheaper per token because more workers = more throughput = more tokens generated per dollar. Queue-only policies waste GPU time on requests that ultimately time out.

A Note on SLA Compliance

Overall SLA compliance is ~30% across all policies. That sounds bad, and it is — but it's a capacity problem, not a policy problem. At 3.0 req/s with Pareto-distributed workloads, queue wait time alone exceeds the per-size P99 targets during sustained load. A single T4 can't clear the queue fast enough. More baseline workers would fix this; policy tuning won't.

What I Learned

1. Composite triggers differentiate under KV stress — 4x more throughput

Queue-only: 227 tok/s and 16.7% success. Composite: 824–968 tok/s with 63–100% success. This is the scenario where dual-signal scaling earns its complexity. If your workload never includes long-context requests, you don't need this.

2. Scaling decisions compound

The burst phase didn't trigger any new scaling. Composite policies had sub-second TTFT in burst because of workers that scaled up during the previous phase. Queue-only policies entered burst with zero spare capacity: 23–27s TTFT. Prior scaling state matters more than current-phase tuning.

3. SLA is a capacity problem, not a policy problem

All policies hit ~30% SLA at 3.0 req/s. The workload genuinely exceeds single-worker capacity. More baseline workers would fix this; policy tuning won't.

4. The real differentiator is KV-aware scaling, not queue threshold tuning

Policies A (queue>5) and B (queue>3) are nearly identical in every metric. The meaningful split is between queue-only and composite. Adding the KV cache signal is what matters — tweaking the queue threshold by 2 is noise. This is like adding a GPU memory alarm vs tuning the SQS depth threshold by 2 messages.

Industry Reality Check — Revisiting in Light of 2026 Production Practice

After this experiment ran, I surveyed what production teams (Red Hat OpenShift AI, KServe, vLLM production-stack, llm-d, NVIDIA Dynamo) actually scale on in 2026. Two corrections to the framing above are worth recording.

Correction 1: Phase 4's "queue depth" was the wrong queue

Phase 4's queue-depth trigger read RabbitMQ broker depth — messages parked at the broker because every worker was at its prefetch cap. The industry-recommended signal is vLLM's internal waiting queue (vllm:num_requests_waiting) — requests already pushed into vLLM that haven't been admitted to the running batch yet. These are not the same signal and they fail in different ways.

Property RabbitMQ broker depth (Phase 4) vLLM num_requests_waiting (industry)
What it measures Messages broker holds because all workers are at prefetch_count cap Requests inside one vLLM engine waiting for KV slots / running-batch room
Granularity Fleet-wide — only fires when every worker is saturated Per-pod — fires when this replica is saturated
Effect of prefetch_count High prefetch hides saturation — broker queue stays empty while vLLM internal queue grows Independent of prefetch — engine reports its own truth
Lag Lags vLLM internal queue by the prefetch buffer depth Direct engine measurement, no transport lag
KEDA scaler rabbitmq scaler — one number per cluster, not per pod prometheus scaler on vllm:num_requests_waiting — per-pod

This re-explains part of why composite policies beat queue-only in Phase 4: RabbitMQ depth was a doubly lagging signal (engine queue grows first, then broker queue grows only after prefetch fills). The KV cache signal was the only thing reading engine state directly. Had Phase 4's queue trigger been vllm:num_requests_waiting instead, the gap between queue-only and composite would likely have been narrower — though composite would still win on sustained KV-bound workloads, for the reasons in Correction 2.

Correction 2: KV-only wins were workload-specific, not universal

The Phase 4 KV-stress workload (long-context, all-XL prompts) created sustained KV pressure. Real production traffic typically spikes and drains. The industry recommendation reflects this:

  • Queue depth (vLLM internal) as primary. Direct measurement of "arrivals outpacing acks." Universal across workload shapes.
  • KV cache utilization as a guard. Two pitfalls flagged by production teams (Red Hat, vLLM project): (a) vLLM pre-allocates KV memory so physical VRAM stays constant regardless of load — the engine-reported fraction can never bottom out, so KV-only can scale up but never scale down cleanly; (b) high KV utilization is often healthy batching, not overload — vLLM at 90% KV may be doing exactly what it should.
  • TTFT / TPOT drift as SLA-coupled triggers. KEDA reads vllm:time_to_first_token_seconds / vllm:time_per_output_token_seconds, scales when p99 drifts past SLO. Scale on what the user actually feels, not on capacity proxies.
  • Frontier (2025–2026): decode tokens-per-second / token velocity. Research (TokenScale, arXiv 2512.03416) argues decode TPS captures queue and KV state implicitly — when either is unhealthy, TPS drops. One signal for both prefill and decode pools in disaggregated setups.
  • NVIDIA Dynamo Planner (GTC 2025). Scales prefill and decode pools separately with different signals because input sequence length stresses prefill while output sequence length stresses decode. Explicitly rejects QPS as misleading.

The corrected industry-aligned signal stack

Tier Signal When it fires
Primary vllm:num_requests_waiting per-pod (Prometheus scaler) Sustained imbalance arrivals > acks at one engine
Guard vllm:gpu_cache_usage_perc Long-output workloads where queue is short but KV is choking
SLA-coupled TTFT p99 / TPOT p99 drift past SLO Scale on the symptom the user feels, not capacity proxies
Frontier Decode TPS (token velocity) Single signal scales prefill + decode coherently
Disagg Separate prefill (ISL-driven) vs decode (OSL-driven) Disaggregated serving (Dynamo, Mooncake) — Phase 8

The corrected Phase 4 framing

Phase 4's "composite KV trigger beats queue-only 4×" is real for sustained-KV-pressure workloads, but it's not the universal recommendation. The cleaner conclusion:

  • Scale on vllm:num_requests_waiting as the default trigger, not RabbitMQ depth — engine-truth, per-pod, prefetch-independent.
  • Add KV utilization as a secondary trigger only when the workload includes long-output requests where the engine queue can stay short while KV chokes.
  • Alert on TTFT/TPOT p99 drift as the SLA-aware safety net — scale on what the SLO contract actually says.
  • Don't read Phase 4's win as "always use composite." Read it as "queue depth at the broker is a doubly lagging signal; the right primary is num_requests_waiting at the engine, with KV as a workload-specific addition." llm-d's Workload Variant Autoscaler is exactly this composite pattern in production.
