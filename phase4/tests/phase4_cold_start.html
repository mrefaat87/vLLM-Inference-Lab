GPU cold start is fundamentally different from CPU cold start. In CPU autoscaling, a new instance is ready in 30–60 seconds. GPU workers carry multi-gigabyte container images, multi-gigabyte model weights, and need to compile CUDA kernels on first use. This is like cold-starting a database replica instead of a stateless web server — there's inherent data gravity.

What We Optimized

S3 Model Cache
60s → 48s (saved ~12s)
Init container downloads model weights from a same-region S3 bucket instead of HuggingFace CDN. Consistent latency, no rate limits, no external dependency. Graceful fallback to HuggingFace if the bucket is missing.
CUDA Warmup
~41s absorbed at startup
Worker sends a synthetic 50-token request before consuming from the queue. Forces CUDA kernel compilation during startup so the first real request isn't slow. Without this, the first user sees ~41s TTFT. With it: ~500ms.
Graceful Drain
0 dropped requests on scale-down
On SIGTERM, worker tracks in-flight asyncio tasks and awaits completion (170s timeout) instead of dropping mid-stream responses. Combined with Karpenter's disruption budget (max 1 node at a time), this gives 100% completion on pod kill.
Karpenter Hardening
Prevents premature scale-down
Disruption budget limits to 1 node at a time. 300s consolidation delay prevents Karpenter from removing a node that just booted. 300s KEDA cooldown prevents thrashing. Without these, we observed workers getting killed during image pull.

The net savings are modest: ~50 seconds off a ~300 second baseline. The CUDA warmup doesn't reduce cold start wall-clock time but shifts the compilation cost from the first user request to startup, which matters more for user experience than raw numbers suggest.

CUDA Warmup in Detail

The first request to a freshly-loaded vLLM instance triggers CUDA kernel compilation — JIT compilation of GPU kernels for the specific model architecture and batch configuration. This adds ~41 seconds to TTFT for that one unlucky request.

The warmup sequence fires a synthetic 1-token request before the worker starts consuming from the queue. The compilation cost is absorbed during startup. Every subsequent request sees normal ~500ms TTFT.

This is JVM warmup for GPUs. The same pattern exists in Java services: you wouldn't send production traffic before the JIT compiler has warmed up hot paths. GPU inference has the same property — first invocation compiles kernels, subsequent invocations reuse them.

What We Didn't Solve

The two largest components of cold start remain untouched: container image pull (~110s) and readiness probe delay (~120s). Together they account for ~230 of the ~250 seconds.

Container Image Pull: 110s of Layer Unpacking

I attempted to eliminate the image pull by pre-baking the vLLM container image into a custom AMI using EBS Fast Snapshot Restore. The hypothesis was that the 110s was network download time for the 3.8GB image.

The hypothesis was wrong. Investigation revealed that the 110s is containerd layer unpacking — decompressing compressed image layers into overlayfs snapshots on the node's filesystem. The download itself completes quickly (the image is cached in the AMI), but containerd still needs to decompress and mount every layer. The AMI cache saved only ~7 seconds.

The bottleneck is decompression, not download. Even with the image bytes already on local disk, containerd must decompress each layer into an overlayfs snapshot. This is sequential and CPU-bound. The fix requires fundamentally changing how images are loaded:

• SOCI (Seekable OCI) — AWS's lazy-loading image format that mounts layers on demand without full decompression. The container starts while layers are still streaming.
• Bottlerocket data volumes — Pre-expanded image layers stored on a separate EBS volume, bypassing containerd's unpack pipeline entirely.

Readiness Probe: 120s of Conservative Safety Margin

The readiness probe uses initialDelaySeconds: 120 — kubelet waits 120 seconds before even checking if the pod is ready. This is a conservative safety margin to prevent kubelet from killing the pod during model weight loading and GPU initialization.

The fix is straightforward but was left for stability: replace the delay with an active probe that polls vLLM's /health endpoint. The pod would become ready as soon as vLLM is actually serving, rather than waiting a fixed 120 seconds. This could save 30–60 seconds depending on how quickly the model loads.

Cold start dropped from ~300s to ~250s. The savings come from S3 model cache (~12s) and shifting CUDA warmup into the startup window. The remaining ~250s breaks down as: Spot provisioning (~90s) + image unpack (~110s) + readiness probe (~50s, overlaps with other steps).

This is why the scaling trigger policy matters so much: it determines when you pay this 250-second cost. Scale too late and users queue for minutes. Scale too early and you pay for idle GPUs at $0.16/hr each. With composite triggers, the policy fires on KV cache pressure ~200 seconds earlier than queue-only, which means the new worker arrives ~200 seconds sooner relative to when it's actually needed.

What I Learned

1. The image pull bottleneck is decompression, not download

Pre-baking the image into the AMI only saved ~7s. The 110s is containerd layer unpacking (decompressing 3.8GB into overlayfs snapshots), not network transfer. This was the most surprising finding — the intuitive fix (cache the image) doesn't address the actual bottleneck.

2. CUDA warmup is the GPU equivalent of JVM warmup

Without a warmup request, the first real user pays ~41s of kernel compilation. A single synthetic request at startup eliminates this entirely. This pattern should be standard in any GPU serving deployment.

3. Karpenter needs guardrails for GPU workloads

Without disruption budgets and consolidation delays, Karpenter would remove nodes that had just started booting workers. The default consolidation behavior assumes stateless workloads that start in seconds — GPU workers that take minutes to initialize need explicit protection.

4. Scale-up latency dominates the autoscaling story

At 14–17 minutes end-to-end, reactive GPU autoscaling can't respond to current load — it can only prepare for the next phase. This makes trigger timing (when to fire) just as important as trigger accuracy (what to fire on). An earlier, slightly noisier trigger can outperform a precise but delayed one.

5. Graceful drain is non-negotiable for streaming workloads

LLM inference generates tokens over 30–120 seconds. Without graceful drain (tracking in-flight tasks and awaiting completion), scale-down kills active streams. The 170-second timeout plus Karpenter's disruption budget gave us 100% completion on pod termination.
